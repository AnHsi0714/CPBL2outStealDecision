# 兩出局該不該跑？——中職教練的跑壘決策指南

2026 台灣棒球數據分析競賽（現場分析戰術組）參賽專案。研究在**第 1–8 局、兩出局、僅一壘有人**的情境下，發動盜壘的損益兩平成功率門檻是多少，以及這個門檻如何隨打者棒次與打者類型改變。

完整研究背景、方法論、時程與分工，請見計畫書：[兩出局一壘有人盜壘決策_專案計畫書.md](./兩出局一壘有人盜壘決策_專案計畫書.md)。

## 核心概念

盜壘失敗（第三出局）會讓該打者的打席保留到下一局重新開始，等於用「打序整體往後延一棒」換取當下的出局風險。傳統 RE24 分析只看當半局的損益，忽略了這個保留效應——這是本研究的核心貢獻。詳見計畫書 1.3、1.4 節。

**重要方法論提醒**：計算「盜壘後的剩餘得分」時，起算點是**盜壘成功的那一球**，不是打席開始或該半局開始；不能直接使用半局總得分，否則會把盜壘之前已發生的得分也算進去，高估 RE。詳見計畫書 3.0 節。

## 快速開始

```bash
pip install requests scipy

python find_2out_first_base.py
```

`find_2out_first_base.py` 預設抓取 2026 年例行賽 GameSno 1–240，篩出第 1–8 局、
兩出局且僅一壘有人的打席，輸出：

- `Outcome=steal_success`：`RequestedRE` 是盜壘成功事件後至當半局結束的剩餘得分。
- `Outcome=steal_failure`：`RequestedRE` 是同隊下一個半局的得分。
- `Outcome=no_steal`：`RequestedRE` 是同隊下一個半局的得分。

逐場原始回應快取於 `data/raw/cpbl/`，分析結果寫入 `outputs/`。若途中中斷，重跑
同一指令會沿用已完成的快取，只重抓缺少的場次。可用參數縮小範圍做測試：

```bash
python find_2out_first_base.py --start 226 --end 240 --delay 1
```

CSV 同時保留當半局剩餘得分、下一半局得分與兩半局合計，方便後續依研究定義調整。

抓取完成後，可執行第一版打者與打序模型：

```bash
python model_batter_decisions.py --simulations 2000
```

若要處理完整 2025 球季：

```bash
python find_2out_first_base.py --year 2025 --start 1 --end 360
python model_batter_decisions.py --year 2025 --start 1 --end 360 --simulations 2000
```

模型使用打者個人的 `1B/2B/3B/HR/BB-HBP/REACH/OUT` 機率，同時模擬：

- 成功：二壘、兩出局、當前打者繼續打，再算到下一個進攻半局結束。
- 失敗：當局結束，下一局保留當前打者開頭。
- 不跑：一壘、兩出局、當前打者繼續打，再算到下一個進攻半局結束。

壘包推進暫時使用聯盟整體、相同 base-out state 與打席結果的經驗分布，尚未加入
個別跑者速度。輸出包含三分支價值、打者出局傷害、打者保留價值與損益兩平成功率。
出局傷害另拆成「非出局時的分支價值」「一次出局的條件成本」與「依打者 OUT%
加權後的預期損失」，避免把高出局率和單次第三出局的傷害混為同一件事。

原本的通用逐球資料匯出仍可執行：

```bash
python CPBL_steal_getData.py
```

`CPBL_steal_getData.py`（原檔名 `getData.py`，跨聯盟資料整併時改名）預設抓 2026 年例行賽 GameSno 226–240，每抓完一場比賽會隨機延遲數秒再抓下一場，避免對 CPBL 官網造成過大負擔。輸出三張 CSV 到 `cpbl_data/` 目錄：

- `cpbl_playbyplay_*.csv`：逐球紀錄（含壘包狀態、累積比分、打序）
- `cpbl_scoreboard_*.csv`：逐局比分（僅供總覽/核對，不可用於 RE 計算，見計畫書 3.0）
- `cpbl_batting_*.csv`：球員整場盒分（含盜壘成功/失敗次數）——這份官方統計現在真的被用來做QA對帳，見下方「引擎驗證」一節的 `validate_steal_parsing.py`

要換抓其他場次，修改檔案最下方的 `YEAR` / `KIND_CODE` / `GAME_SNO_START` / `GAME_SNO_END`。

`KBO_steal_getData.py`／`MLB_steal_getData.py` 是同樣模式的另外兩個聯盟爬蟲，`combine_leagues.py` 把三份 playbyplay CSV 統一欄位命名（`Outs`／`On1B`／`On2B`／`On3B` 等）後合併成一份跨聯盟資料集，供計畫書「跨聯盟比較」項目使用。

## 資料使用注意事項

- 野球革命 Open Data 依 **ODC-By** 授權，使用時須標註來源。
- CPBL 官網資料屬自行爬蟲取得，請留意其使用條款並控制爬取頻率；原始資料與程式碼分開管理，**不建議把大型原始資料檔（CSV/JSON）進版控**。
- Open Data 與 CPBL 官網資料均含部分人工紀錄成分，盜壘等事件性紀錄須留意判讀誤差，詳見計畫書「已知限制」。
- **CPBL 逐球資料含「換投手／代打／代跑／守備／選手」等純公告列**（不是真正的投球事件），這種列的 `OutCnt`／壘包欄位是殘留自公告發生當下、尚未被下一球更新的舊值，最常出現在半局交替或臨場換人時刻。若未過濾，會被誤判成真實比賽狀態（實測約占全部列數 3%），集中污染「兩出局、空壘」這類半局尾聲常見的狀態。過濾邏輯（`is_administrative_only_row`／`remove_administrative_rows`）抽在獨立的 `cpbl_row_filters.py`（避免 `find_2out_first_base.py`／`CPBL_steal_getData.py` 互相 import 造成循環依賴），`find_2out_first_base.py`、`CPBL_steal_getData.py`、`build_re24_matrix.py`、`model_batter_decisions.py` 均已套用；`find_2out_first_base.py` 本身的 1,877 筆決策樣本經重跑確認筆數不變，不受影響。詳見下方「引擎驗證」一節。

## RE24 矩陣與熱力圖

計算中職專屬的 24 種 base-out state 得分期望值矩陣，並輸出熱力圖報告：

```bash
python build_re24_matrix.py --year 2025 --start 1 --end 360
python generate_re24_report.py --year 2025 --start 1 --end 360
```

- `build_re24_matrix.py`：把每個半局切成連續的 base-out state 區段（壘包或出局數一變就是新區段，涵蓋打席內盜壘造成的狀態切換），每個區段的起算比分取自該區段第一球事件發生前的累積比分，剩餘得分＝半局結束比分－起算比分，只計入 `half_is_complete` 判定為已打完的半局。方法與 3.0 節的「起算點對齊到事件本身」原則一致，且重用 `find_2out_first_base.py` 已驗證過的壘包/比分/半局完整性判定邏輯。2025 年 360 場例行賽共取得 27,699 個 state 區段（已排除公告列污染，見「引擎驗證」一節）。同時輸出層次二基礎損益兩平門檻（`RE(一壘)/RE(二壘)`，未計保留效應）：2 出局約 70.2%，與計畫書提到的 MLB 參考值（約 69%）量級相近，可作為方法論交叉驗證。
- `generate_re24_report.py`：把矩陣畫成互動熱力圖（`reports/cpbl-re24-matrix-2025.html`），純 HTML/CSS，不依賴圖表套件；每格可 hover／Tab 顯示樣本數與標準差，並附完整資料表供核對。

可直接用瀏覽器開啟 [reports/cpbl-re24-matrix-2025.html](reports/cpbl-re24-matrix-2025.html)。

## 引擎驗證：模擬能否重現真實 RE24

計畫書 3.1 節要求：「模擬引擎若無法重現實際 RE24，代表引擎有誤，不可繼續往下做」。用 `model_batter_decisions.py` 同一套抽樣引擎（打者機率分布＋聯盟壘包推進經驗分布），從 24 種 base-out state 各自模擬起跑，跟真實 RE24 矩陣逐格比較：

```bash
python validate_re24_simulation.py --year 2025 --start 1 --end 360
```

- 修正資料品質問題（見上方「資料使用注意事項」）後，24 格整體相關係數 **r = 0.992**，加權平均誤差 **0.033 分**，誤差最大的幾格都落在樣本數較少（n < 400）的稀有壘包組合，屬合理抽樣雜訊，不是系統性偏誤。
- **修正前**這項檢查曾抓到一個真實 bug：「2 出局、空壘」這格模擬值只有真實值的一半（0.10 vs 0.23），且剛好是樣本數最大的一格（n=5,533），不像雜訊。追查後發現是上述的公告列污染——它把「0 出局、空壘」半局開局的整局得分，錯誤地灌進了「2 出局、空壘」這格，把它的平均墊高了將近一倍。修正後這格降到 0.096，也讓「2 出局、一壘有人」（0.204）正確地高於「2 出局、空壘」（0.096），符合棒球常識（先前修正前兩者顛倒，一直沒被注意到）。
- 對 `model_batter_decisions.py` 的模擬結果影響很小：全季損益兩平門檻中位數從 58.1% 微調為 **58.5%**，逐棒次與打者類型的結論方向、顯著性均未改變（見下方最新數字）。

### 盜壘文字判讀對帳：跟 CPBL 官方統計核對

上面驗證的是「模擬引擎」，這裡驗證的是完全不同的另一件事：`find_2out_first_base.py` 判斷「這球是不是盜壘、成功還是刺殺」全靠比對 `Content` 自由文字（`is_steal_success`／`is_steal_failure`），這段文字判讀邏輯本身準不準，從來沒有拿獨立資料源核對過。CPBL 官方 box score（`BattingJson` 的 `StealBaseOKCnt`／`StealBaseFailCnt`）剛好是另一組獨立統計的盜壘數字，可以拿來對帳：

```bash
python validate_steal_parsing.py --year 2025 --start 1 --end 360
```

用同一套文字判讀邏輯的通用版（不限「兩出局、一壘有人」，涵蓋全場任何時機的盜二／三壘、雙盜壘、盜壘刺），逐場逐隊加總，對照官方數字。2025 年 360 場：

| | 文字解析加總 | CPBL 官方加總 |
|---|---|---|
| 盜壘成功 | 508 | 508 |
| 盜壘刺 | 242 | 242 |

720 個（場次, 球隊）組合**完全沒有不相符**。過程中修正了兩個文字判讀的邊界情況：

- **盜壘刺但因野手失誤反而安全上壘**（`一壘跑者X 盜壘刺-因野手失誤進壘上二壘。`）：官方仍把這次算進盜壘刺（跑者被判出局在先，失誤是另一件事），原本的規則會直接漏掉。
- **原住民選手全形間隔號名字過長**（如「吉力吉撈．鞏冠」）：原本判讀規則裡「跑者名字跟動作描述之間最多幾個字」抓太緊，比一般漢字姓名長的名字會直接配不上，導致雙盜壘漏算。

這個對帳結果同時也回答了 `find_2out_first_base.py` 1,877 筆決策樣本的一個潛在疑慮：既然全場所有盜壘事件的文字判讀都能 100% 對上官方統計，兩出局、一壘有人這個子情境（`is_steal_success`／`is_steal_failure` 用的是同一套規則）的判讀正確性也有了獨立佐證，不只是內部的壘包狀態變化交叉驗證（`EventTransitionMatches`）而已。

## 棒次 × 打者類型分組分析

在跑完 `find_2out_first_base.py` 與 `model_batter_decisions.py` 之後，可依序執行以下腳本，
分析「前段(1-5)/後段(6-9)棒次」與「長打型(ISO代理)/選球型(BB%代理)打者」如何影響盜壘損益兩平門檻：

```bash
python analyze_batter_types.py --year 2025 --start 1 --end 360
python join_decision_batter_types.py --year 2025 --start 1 --end 360
python flag_lineup_substitutions.py --year 2025 --start 1 --end 360
python compare_groups.py --year 2025 --start 1 --end 360 --input outputs/cpbl_decision_with_starter_flag_2025_A_1-360.csv
python generate_decision_report.py --year 2025 --start 1 --end 360
```

- `analyze_batter_types.py`：只取當季打席數 ≥ 100 的打者，算出 `ISO_proxy`（長打力代理，=P_2B+2×P_3B+3×P_HR）與
  `BBpct_proxy`（選球力代理，=P_BB_HBP），再以聯盟中位數切成高/低兩組。依計畫書 3.2 節，刻意不用 SLG/OBP 避免兩指標高度重疊。
  另外會逐球掃描 `data/raw/cpbl/*/game_*.json` 算出每位打者當季最常打的棒次（眾數），輸出 `PrimaryLineupGroup`（前段1-5/後段6-9）——
  **這是打者本人的固定屬性**（跟 PowerGroup/TTOGroup 等一樣，同一位球員無論哪天代打排第幾棒都不變），不是「這一局剛好排第幾棒」的
  情境變數；兩者是不同的東西，見下方 `generate_decision_report.py` 的說明。
- `join_decision_batter_types.py`：把棒次分組與打者類型分組貼到每一筆決策上；這裡的 `LineupGroup` 是「這一筆決策當下實際排第幾棒」，
  是決策層級的情境變數，跟 `analyze_batter_types.py` 算出的 `PrimaryLineupGroup`（打者本人固定屬性）故意分開、各有用途，不要混用。
  打席數不足的打者分組欄位留空，不納入類型分組比較。
- `flag_lineup_substitutions.py`：標記該筆決策當下，該棒次是先發打者還是代打/換人後（用同場同隊該棒次第一次出現的打者視為先發）。
  2025 年資料顯示代打影響可忽略（逐棒次中位數門檻差異均 < 0.6 個百分點），故後續分析未特別排除代打情境，僅留欄位供追溯。
- `compare_groups.py`：用 Mann-Whitney U 檢定比較各分組的損益兩平門檻中位數（需要 `scipy`），並輸出逐棒次(1-9)門檻分解與交叉表。
- `generate_decision_report.py` 讀到 `cpbl_group_comparison_*.json` 時，會自動在報告加入「棒次與打者類型如何影響門檻」區塊；
  找不到該檔案時會略過此區塊並印出提醒，不影響其餘內容產生。
- 同一支腳本也會讀 `cpbl_batter_types_*.csv`（用 `HitterAcnt` 查表），在「逐筆重算」的個案 explorer 裡，每筆決策的打者名字下方會多一排標籤，
  顯示**這位打者本人**是前段/後段棒次型、以及長打/選球/上壘率/接觸/TTO 五種分組各自的高低——這排標籤用的是 `PrimaryLineupGroup`（球員固定屬性），
  跟案例標題本來就會顯示的「這筆決策當下是第幾棒」（情境事實）是兩件不同的東西，不會互相混淆。打席數 < 100（不夠格分組）的打者會顯示
  「打席數不足」而非留空。「符合門檻的跑者名單」的每位跑者名字下方也用同一份資料，附上同樣的固定球員類型標籤，方便直接辨識這位跑者本身是哪種打者。

### 2025 分析結果：棒次如何影響門檻

逐棒次（1–9）損益兩平門檻中位數：

| 棒次 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 | 9 |
|---|---|---|---|---|---|---|---|---|---|
| 門檻 | 55.0% | 57.3% | 56.0% | **61.9%** | 58.8% | 57.9% | 56.5% | 60.3% | 60.0% |

門檻幾乎完全由「V不跑－V失敗」這個分子決定，「V成功－V失敗」（盜壘成功能省下多少）在各棒次都差不多，不隨棒次變。分子大小才是關鍵，拆解如下：

- **第 1、3 棒門檻最低（55%–56%）**：不管盜壘失敗被保留、還是不跑正常出局後換下一棒，接手的都是實力相近的早段棒次，兩種情況差距小，是全場相對最適合冒險盜壘的棒次。
- **第 4 棒門檻最高（61.9%）**：主因是「這位打者自己夠強」——續打時常能靠自己的打擊在本半局多得分，但盜壘刺會立刻結束半局，等於白白放棄這個打席的價值。這是「打者自身能力」驅動的效應。
- **第 8、9 棒門檻並列次高（60.3%／60.0%，差距在雜訊範圍內）**：這兩棒的共通點是「保留效應」——正常情況下這兩棒出局後，下一局很快輪到全隊前段棒次開路；但盜壘刺會讓自己被保留、下一局改由自己先打，等於賠掉了讓前段棒次提前登場的機會。這是「打序被延後一棒」驅動的效應，也是本研究最初設定要驗證的核心機制。第 8 棒略高於第 9 棒（過去以為第 9 棒是唯二次高點，資料品質修正後兩者幾乎打平，值得留意但不影響核心論點）。
- **第 2、5–7 棒門檻居中（57%–59%）**：實力較平均的一段，銜接的下一棒實力也差不多，「打者自身能力」跟「保留效應」都不明顯。

換句話說，門檻高不是單一原因，而是「這位打者自己多強」跟「盜壘失敗會不會卡住更強棒次的機會」兩股力量疊加，且兩者在打線的不同位置各自主導——第 4 棒是前者主導、第 8、9 棒是後者主導，不能用同一套理由解釋。

長打型／選球型打者（PA ≥ 100，聯盟中位數切分）的比較：

| 分組 | 高長打 | 低長打 | 高選球 | 低選球 |
|---|---|---|---|---|
| 門檻中位數 | 60.7%（n=958） | 55.7%（n=756） | 60.0%（n=918） | 56.7%（n=796） |

兩個差異都極顯著（p < 0.001），且在前段(1-5)／後段(6-9)棒次分開看依然成立。結論是：**這位打者整體打擊能力愈強（不管展現在長打還是選球），愈不該冒險盜壘**，長打力與選球力兩者方向一致，跟計畫書原先設想「長打型 vs 選球型互相抵銷」不完全相符，這點在簡報裡值得特別強調。

### 「上壘率」不是單一概念：兩個容易混淆的假設要分開驗證

計畫書在兩處用了不完全相同的「打者類型」框架：1.4 節談的是「高長打型」vs「**高上壘接觸型**」（單打即可得分），3.2 節的操作型定義則是「ISO（長打力）」vs「**BB%（選球力）**」。這兩組對照不是同一件事——「靠安打上壘」跟「靠保送上壘」是不同能力，套用哪一個公式會得到不同、甚至相反的結論，分析時務必先講清楚驗證的是哪一個假設。

三種「上壘」相關指標跟長打力（ISO_proxy）的相關係數、以及各自分組後的門檻比較：

| 指標 | 定義 | 與 ISO 相關係數 | 高組門檻 | 低組門檻 | p 值 |
|---|---|---|---|---|---|
| BBpct_proxy（選球力，3.2 節公式） | 保送/觸身率 | 0.333 | 60.0%（n=918） | 56.7%（n=796） | < 0.001 |
| OBP_proxy（真上壘率） | 安打率+保送觸身率 | 0.460 | 58.2%（n=1028） | 58.6%（n=686） | 0.266（不顯著） |
| **SingleRate_proxy（純接觸型，1.4 節概念）** | 單打率 | **-0.369** | **55.5%（n=884）** | **62.8%（n=830）** | **< 0.001** |

三個指標方向不一致：**選球力愈高，門檻愈高**（更不該跑）；但**真上壘率愈高，門檻反而幾乎持平甚至略低**（差異不顯著），效應主要在後段棒次；把上壘率拆解到最乾淨的**純單打率**後，方向更明確、差距也最大（7.3 個百分點，是所有分組比較裡最大的），且與 ISO 是負相關而非正相關，代表這是三者中跟長打力切得最乾淨的一個。

- **選球力（BB%）**：保送頂多把一壘跑者擠到二壘，通常送不回本壘，對「這半局能不能立刻多得分」幫助有限，卻讓打者本身更容易被保留在場上，所以門檻被拉高。
- **純單打率**：直接對應計畫書「單打即可得分」的邏輯——這類打者一旦上場最可能就是單打，而單打能不能把跑者從一壘送回本壘高度依賴壘包位置（從二壘幾乎都能回來，從一壘常常不行），讓跑者先偷上二壘的邊際價值特別高，因此門檻大幅下降，**清楚驗證了計畫書 1.4 節「高上壘接觸型該更常跑」的假設**。
- **真上壘率（OBP）**：因為同時包含安打（拉低門檻）與保送（拉高門檻）兩種方向相反的成分，兩者混在一起互相抵銷，訊號比純選球力或純單打率都髒——這正是計畫書 3.2 節堅持用 ISO／BB% 而非 SLG／OBP 分組的原因。

**結論**：如果簡報要驗證「打者類型如何影響盜壘決策」，長打力用 `ISO_proxy`、選球力用 `BBpct_proxy`、接觸力用 `SingleRate_proxy` 三個指標分開呈現最乾淨；`OBP_proxy` 可以放在附錄，當作「為什麼不能直接用上壘率」的方法論佐證。

## 六隊決策品質評估

對應計畫書 3.1 節「層次四」：把模擬算出的門檻拿去跟各隊實際盜壘行為交叉比對，判斷球隊實際上有沒有跑對。

```bash
python analyze_team_decisions.py --year 2025 --start 1 --end 360
python generate_decision_report.py --year 2025 --start 1 --end 360
```

- `analyze_team_decisions.py`：讀 `cpbl_decision_model_*.csv`，依 `BattingTeam` 分組，計算每隊在兩出局、一壘有人情境下的：
  - **該隊門檻**——該隊所有決策機會（不論當時有沒有跑）的 `BreakEvenSuccessRate` 中位數
  - **實際成功率**——該隊盜壘嘗試（成功+失敗）中，成功的比例，並算 Wilson 95% 信賴區間
  - **判定**——不是直接比大小，而是用二項檢定（`scipy.stats.binomtest`）檢驗「實際成功次數」是否顯著偏離「真實成功率＝該隊門檻」這個假設：**p < 0.05 才判「跑對」或「跑錯」**，否則標記「無法判定（不顯著）」；嘗試次數為 0 時直接標記「樣本不足（無嘗試）」，不進行檢定。
  再依前段（1–5棒）／後段（6–9棒）各拆一次，同一套邏輯。
- `generate_decision_report.py` 讀到 `cpbl_team_decisions_*.json` 時，會自動在報告加入「六隊決策品質評估」區塊；找不到該檔案時會略過此區塊並印出提醒，不影響其餘內容產生。

**為什麼不直接比「實際成功率」跟「門檻」的大小**：2025 年各隊兩出局、一壘有人的盜壘嘗試只有 27–49 次，這種樣本量下，點估計的成功率離門檻差個 3–5 個百分點很可能只是抽樣雜訊，不是球隊真的決策錯誤——例如富邦悍將實際成功率 55.0% 略低於自己門檻 58.5%，看起來像跑錯，但二項檢定 p = 0.749（95% CI 是很寬的 [39.8%, 69.3%]，把門檻整個包在區間裡），完全不顯著。六隊裡只有統一7-ELEVEn獅（79.2% vs 58.9%，p = 0.005）通過顯著性檢定，其餘五隊都無法判定。這也直接呼應計畫書 3.3 節「『有跑 vs 沒跑』實證比較切層後樣本不足，須誠實揭露」的提醒，以及第 7–8 週待辦的「敏感度分析與 bootstrap 信賴區間」——這裡先用二項檢定把同樣的統計把握力問題做掉。

**只做「跑對／跑錯」，不做「該跑不跑」**：後者是指「條件有利卻很少嘗試」，需要額外定義一個「嘗試率」基準才能判斷，但這裡的樣本量本來就撐不起跑對/跑錯的顯著性判定了，更撐不起額外一個嘗試率基準的判定，故此處先誠實省略，留待跨年度資料補齊後再處理。

### 2025 分析結果：六隊跑對還是跑錯

| 球隊 | 決策機會 | 盜壘嘗試 | 實際成功率（95% CI） | 該隊門檻 | p 值 | 判定 |
|---|---|---|---|---|---|---|
| 統一7-ELEVEn獅 | 304 | 48 | 79.2%（65.7–88.3%） | 58.9% | **0.005** | **跑對** |
| 味全龍 | 335 | 45 | 71.1%（56.6–82.3%） | 60.8% | 0.172 | 無法判定 |
| 台鋼雄鷹 | 305 | 49 | 67.3%（53.4–78.8%） | 58.2% | 0.246 | 無法判定 |
| 中信兄弟 | 300 | 27 | 66.7%（47.8–81.4%） | 58.7% | 0.441 | 無法判定 |
| 樂天桃猿 | 312 | 40 | 60.0%（44.6–73.7%） | 55.7% | 0.635 | 無法判定 |
| 富邦悍將 | 321 | 40 | 55.0%（39.8–69.3%） | 58.5% | 0.749 | 無法判定 |

全聯盟：249 次嘗試，實際成功率 67.1%，門檻中位數 58.5%。六隊裡只有**統一7-ELEVEn獅**一隊在統計上顯著跑對；其餘五隊（包含點估計最低的富邦悍將）都無法判定——不是「跑錯」，而是這個樣本量下看不出跟門檻有顯著差異，誠實地說就是「不知道」。

## 符合門檻的跑者名單

對應計畫書「具體球員應用」：把層次二/三算出的損益兩平門檻，對照到具體球員身上，列出哪些跑者的當季實際盜壘能力夠格冒險。

```bash
python analyze_runner_steal_rates.py --year 2025 --start 1 --end 360
python generate_decision_report.py --year 2025 --start 1 --end 360
```

- `analyze_runner_steal_rates.py`：直接掃描 `data/raw/cpbl/*/game_*.json` 逐球紀錄，用 `is_steal_success`／`is_steal_failure`（`find_2out_first_base.py`）找出**一壘跑者盜二壘**的成功/失敗事件——刻意只算這一種，不含盜三壘、雙盜壘，那是另一種跑壘能力，混進來會稀釋「這位跑者盜二壘準不準」這個問題本身。
  - **跑者身分解析**：事件列的 `FirstBase` 欄位在事件當下就是跑者所在棒次（1–9），往回找同一半局、同棒次最近一次有 `HitterAcnt` 的打席列即可還原真實身分——以 `HitterAcnt` 為主鍵，不用姓名 join。2025 年全季 681 次事件 100% 解析成功。
  - **判定刻意不比對單一門檻**：門檻本身就是「隨下一棒棒次而變」（1–9 棒門檻中位數 55.0%–61.9%，見 `cpbl_decision_model_*_summary.json` 的 `by_hitter_lineup`）——這正是計畫書 3.1/3.2 節花整節篇幅建立的核心發現。如果把每位跑者的成功率拿去比對一個全季中位數，等於把「門檻會隨打者變動」這個結論本身丟掉，退化成一個跟球員類型無關的假判定。因此改成逐棒次比對：每位跑者的季成功率分別對照 1–9 棒各自的門檻，分成四級——
    - **任一棒次都可跑**：成功率高過全部 9 棒門檻，換誰上都不用猶豫。
    - **視下一棒棒次而定**：部分棒次值得跑、部分不值得，判定要看「現在是第幾棒在打擊」。
    - **任一棒次都不建議跑**：連門檻最低的棒次都不夠格。
    - **樣本不足**：嘗試次數 <（預設）5 次，樣本太少不下判定。
  - **只用單季資料**：球員可能轉型或老化，教練現在該不該派他跑要看這一季的實際表現，不跨季合併平均。
- `generate_decision_report.py` 讀到 `cpbl_runner_steal_rates_*.json` 時，會自動在報告加入「符合門檻的跑者名單」區塊——表格附一排 1–9 棒的小方格，逐格標示該跑者在那個棒次可跑（綠）或不建議（紅），可搜尋球員/球隊、可依判定篩選；找不到該檔案時會略過此區塊並印出提醒。

### 2025 分析結果

103 位有過至少 1 次盜二壘嘗試的跑者：**24 位任一棒次都可跑**、**8 位視下一棒棒次而定**、**16 位任一棒次都不建議跑**、55 位樣本不足（嘗試 < 5 次）。例如陳聖平（統一7-ELEVEn獅，13 次嘗試 61.5% 成功率）除了門檻最高的第 4 棒（61.9%）以外，其餘 8 棒都夠格跑；門檻最低的第 1 棒（55.0%）到門檻最高的第 4 棒（61.9%），同一位跑者可能一個「可跑」、一個「不建議」，判定本來就該跟著打者換。
